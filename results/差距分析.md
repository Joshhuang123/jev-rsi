# 差距分析 · 零训练 67.3% vs 上游微调 88.0%

> 2026-11-02。数据来源：tev1 官方仓库 `runs/new-v1/` + 本机实测的 1000/300 条逐条结果。
> **结论先说：20.7 个点的差距，不是均匀分布的，而是集中在 policy 一个来源上。**

---

## 一、差距在哪：逐源拆解

同一份评测集（`records_sha256 = 0b94c253...`，与上游 `evaluation.json` 的哈希**完全一致**），
同一套协议（temperature=0 / max_tokens=8 / logprobs=true / top_logprobs=5 / 关闭思考）。

| 来源 | 题数 | 上游微调 | 本机零训练 | 差距 |
|---|---:|---:|---:|---:|
| ag_news | 100 | 87.0% | 87.0% | **+0.0** |
| boolq | 200 | 90.5% | 82.0% | +8.5 |
| banking77 | 200 | 90.5% | 75.5% | +15.0 |
| mnli | 250 | 91.6% | 70.0% | +21.6 |
| sst5 | 100 | 52.0% | 35.0% | +17.0 |
| **policy** | 150 | **100.0%** | **40.7%** | **+59.3** |
| **合计 test** | 1000 | **88.0%** | **67.3%** | **+20.7** |
| **policy_transfer** | 300 | **100.0%** | **43.3%** | **+56.7** |

**读法**：把 policy 剔掉，其余五个来源上零训练已经能拿 75.9%（微调 87.0%），差距只有 11 个点。
**20.7 个点里，policy 一个来源就贡献了 13.9 个点**（150 题 × 59.3%）。

---

## 二、微调到底买到了什么：一个模板 + 三值逻辑

把 policy 的原始数据拆开看，差距的本质就清楚了。

### 2.1 policy 题目长什么样

```json
{
  "state": {
    "policy": "Eligible if and only if (days_since_purchase <= 362 AND NOT (item_unopened is true)). Unspecified facts are unknown; do not assume they are false.",
    "record": { "days_since_purchase": 357, "item_unopened": true, "order_value_usd": 9215 }
  },
  "question": "Is the record eligible under the supplied policy? Use only the provided facts.",
  "options": [
    { "label": "A", "key": "ineligible", "description": "Ineligible." },
    { "label": "B", "key": "eligible",   "description": "Eligible." },
    { "label": "C", "key": "unknown",     "description": "Insufficient information to determine eligibility." }
  ]
}
```

**三个选项不是「二选一 + 弃权」，而是三个都对的三值逻辑答案**：
`eligible`（真） / `ineligible`（假） / `unknown`（**信息不足**）。

最后一项才是关键。题干写着「Unspecified facts are unknown; do not assume they are false」——
**模型必须判断「这条规则依赖的事实里，有没有哪个没给」**。这不是查表，是三值 Kleene 逻辑。

### 2.2 训练与测试的分布

| | 训练集 | test | policy_transfer |
|---|---|---|---|
| policy 条数 | 1500 | 150 | 300 |
| 树形模板 | 4 种（2 层） | **同样 4 种（2 层）** | **2 种全新（3 层嵌套）** |
| 来源生成器 | `policy-v1` | `policy-v1` | `policy-v1` |

train 的 4 种树：`and(a,b)` · `or(a,b)` · `and(a,not(b))` · `or(and(a,b),c)`
test 用的**就是这 4 种**（比例也接近）
policy_transfer 用的是 **train 里完全没出现过的 3 层嵌套**：
`and(or(a,b),not(c))` · `or(and(a,not(b)),and(not(a),c))`

### 2.3 所以「策略迁移」是名副其实的

- **test 里的 policy**：同模板不同数值 → 考的是**在该模板内的泛化**
- **policy_transfer 里的 policy**：新树形 → 考的是**能否把组合规则本身迁移到没见过的结构**

微调把 policy 从 40.7% 拉到 100%、把 policy_transfer 从 43.3% 拉到 100%，
说明它学到的**不是背答案，是「按逻辑树逐层求值 + 识别缺失事实」这套程序**。

## 三、有没有作弊的嫌疑：查过了，没有

三条最容易被质疑的点，逐条核实：

### 3.1 test 是不是在训练集里？

**没有。** 精确比对（排除 gold/label 等答案字段后取全字段签名）：

| 比对 | 重合数 |
|---|---|
| test 1000 条 vs train | **0** |
| test 里 policy 150 条 vs train | **0** |
| policy_transfer 300 条 vs train | **0** |
| test policy 的 `state` 出现在 train | **0/150** |

上游自己的 `dataset-manifest.json` 也记了：`cross_split_group_overlap: 0`、
`cross_split_normalized_state_overlap: 0`、`cross_split_exact_prompt_overlap: 0`。

### 3.2 是不是靠选项位置记答案？

**不是。** 选项顺序是打乱的：

| | 前 5 条的 option key 顺序 |
|---|---|
| train | (ineligible, eligible, unknown) ×2 · (ineligible, unknown, eligible) · (eligible, unknown, ineligible) |
| test | (ineligible, unknown, eligible) · (unknown, eligible, ineligible) ×2 · (unknown, ineligible, eligible) ×2 |
| policy_transfer | (unknown, eligible, ineligible) ×2 · (eligible, ineligible, unknown) · (ineligible, unknown, eligible) |

答案字母分布也均衡：train policy A/B/C = 492/489/519，test policy = 44/45/61。

### 3.3 上游自己怎么说？

`runs/new-v1/README.md` 原文：

> **These benchmarks were reused during development. They are not untouched test results**
> and do not establish calibrated confidence, general accuracy, or an untuned-base comparison.

**这句话要当真。** 88.0% 是在**开发过程中复用过的基准**上测的，不是留出集。

但注意这不等于「分数虚高」：
- 复用的是**基准本身**（题目集被反复用来迭代），不是「训练时偷看过测试答案」；
- 训练数据与测试集零重合，已独立验证；
- 上游自己保留了 paired 对比：`baseline_correct: 852/1000`（85.2%）——
  **他们那个「older model 基线」已经有 85.2%**，比本机零训练的 67.3% 高 17.9 个点。
  → **上游的 88.0% 不是「从 67% 涨到 88%」，而是「从 85.2% 涨到 88%」，只涨 2.8 个点。**

### 3.4 结论：88.0% 的 20.7 个点里，有多少是「模型好」，多少是「基线不同」

| | 数值 | 说明 |
|---|---|---|
| 本机零训练（Qwen3.5-4B base + prompt 协议） | 67.3% | 我们实测 |
| 上游记录的 paired baseline（老模型） | 85.2% | 上游自己记的，未说明是哪个模型 |
| 上游微调版 | 88.0% | 上游实测 |

**上游那个 85.2% 的基线身份不明，README 只说是 "older model"。** 这是整个对比里最大的未知数：
如果它也是一个「指令遵循良好但没做 SFT 的 instruct 模型」，那
**真正的「微调增益」只有 2.8 个点，而不是 20.7 个点。**

## 四、所以「差 20.7 个点」这个说法该怎么改写

原写法：「零训练 67.3%，微调 88.0%，差 20.7 个点」—— **这个说法会让人误以为微调值 20.7 个点。**

准确写法：

> 在同一份评测集、同一套协议下，**未经 SFT 的 Qwen3.5-4B base 拿到 67.3%**，
> 上游 SFT 后的版本报 88.0%。
> **差距集中在 policy 一个来源**（+59.3），其余五个来源平均只差 11 个点，ag_news 甚至完全相同。
>
> 微调买到的具体能力是：**读懂一段布尔策略规则、逐层求值、并在事实缺失时选「unknown」**。
>
> 但 88.0% 是在**开发中复用过的基准**上测的（上游自己声明），
> 且上游记录的 paired baseline 已有 85.2%——
> **所以「微调到底值多少分」这件事，上游的数据不足以回答**，需要在我们自己的基线上重训一版做配对对比。

---

## 五、下一步怎么做才能真答「微调值多少分」

现在缺的不是算力，是**配对基线**。三个选项：

| 方案 | 做法 | 能回答什么 |
|---|---|---|
| **A. 用同一份数据自训** | 用 tev1 的 37,840 条配方 + 官方 `data/v1/records/train.jsonl`，在本机 MLX 上 LoRA 训一版 Tev1 4B | 唯一能得出「本机基线 67.3% → 训练后 X%」的干净配对对比 |
| **B. 换更强底座** | 同一个 prompt 协议，换成 instruct 版 Qwen3.5-4B 或更大的模型跑零训练 | 先看「不训能不能到 85%+」，确定要不要训 |
| **C. 先做诊断** | 只看 policy 那一组：把零训练基线在 policy 上的 150 条逐条读出来，看它错在哪（是算错逻辑、还是选不出 unknown） | 不用训模型就能知道差距是「不会算」还是「不知道要选 unknown」 |

**建议 C → A**。C 几乎零成本，而且直接决定 A 值不值得做：
如果零训练模型在 policy 上**能算对布尔逻辑、只是分不清 unknown**，
那 A 的收益会很大；反过来如果它连布尔都算错，
说明 base 模型缺的是基础能力，SFT 也未必能补。
